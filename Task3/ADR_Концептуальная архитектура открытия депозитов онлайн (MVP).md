Основные потоки: 
######  **Поток A. Заявка с сайта (новый клиент):**

1. Клиент открывает сайт → API Gateway → Сервис ставок (кэш) → список ставок.
2. Клиент отправляет Ф. И. О. и телефон → API Gateway → Сервис заявок.
3. Сервис заявок сохраняет заявку (статус «Новая») и публикует событие в Kafka.
4. Адаптер кол-центра создаёт обращение; менеджер видит заявку.
5. Менеджер при необходимости фиксирует особую ставку через Сервис ставок.
6. Клиент получает СМС с приглашением в отделение.
7. В отделении сотрудник проводит KYC и открывает депозит в АБС.
8. АБС-адаптер получает статус «Депозит открыт» → Kafka → Сервис заявок → Сервис уведомлений → СМС клиенту.

###### **Поток B. Заявка в интернет-банке (существующий клиент):**

1. Клиент открывает ИБ → API Gateway → Сервис ставок (общие и персональные ставки).
2. Клиент выбирает счёт и сумму → API Gateway → Сервис OTP → СМС-шлюз → СМС с кодом.
3. Клиент вводит код → Сервис OTP подтверждает → Сервис заявок создаёт заявку.
4. Сервис заявок публикует событие → АБС-адаптер передаёт заявку в staging Oracle.
5. Задание АБС обрабатывает заявку; менеджер бэк-офиса подтверждает условия в АБС.
6. Статусы «Ставка подтверждена» и «Депозит открыт» возвращаются через staging → Kafka → Сервис заявок → Сервис уведомлений → СМС клиенту.

###### **Поток C. Управление ставками:**
1. Менеджер депозитного или кредитного бэк-офиса открывает админ-UI Сервиса ставок.
2. Создаёт/изменяет ставку; система проверяет RBAC, сохраняет версию.
3. Изменение публикуется в кэш; сайт и ИБ видят актуальные ставки.
4. История изменений доступна для аудита.
### 3.3. Логика принятия решений

1. **Изоляция каналов от АБС.** Сайт и ИБ не обращаются к АБС напрямую. Между ними и АБС находятся API Gateway/BFF, Сервис депозитных заявок, Сервис ставок и АБС-адаптер. Это снимает риск перегрузки АБС и позволяет выполнить NFR-02/NFR-03.
    
2. **Интернет-банк не переводим полностью на микросервисы в MVP.** Депозитные экраны добавляются в существующий монолит ИБ, который вызывает новые сервисы по REST. Это сохраняет текущую аутентификацию, сессии и дизайн-систему, не требует совместимости монолита с Kafka (NFR-05) и снижает риск MVP.
    
3. **Kafka используем внутри нового контура.** Новые сервисы (Java Spring Boot) публикуют и потребляют события через Kafka. ИБ и сайт Kafka не видят. Это соответствует целевому направлению S-03 и не блокирует MVP.
    
4. **АБС-адаптер через staging-таблицы Oracle.** Вместо онлайн-API АБС используем существующий паттерн интеграции по БД: адаптер пишет заявки и команды в staging-таблицы, задание АБС (PL-SQL) обрабатывает их с заданной частотой и возвращает статусы. Это использует экспертизу PL-SQL, не нагружает АБС онлайн-запросами и позволяет регулировать поток.
    
5. **Сервис ставок — единый источник истины.** XLS/email заменяются Сервисом ставок с административным UI, RBAC и историей версий. Сайт и ИБ читают ставки из кэша. Альтернатива «ставки в АБС» отклонена: АБС перегружена, а выпуск изменений в АБС медленный и рискованный.
    
6. **OTP и уведомления — отдельные сервисы банка.** Не меняем ядро ИБ у подрядчика (S-06). Сервис OTP генерирует и проверяет коды, Сервис уведомлений отправляет СМС через существующий СМС-шлюз.
    
7. **Событийная согласованность с outbox.** Сервис заявок пишет заявку и событие в одну транзакцию (outbox), затем публикует в Kafka. Потребители идемпотентны. Это даёт надёжную доставку статусов и уведомлений.
    
8. **HA и масштабирование.** Новые сервисы stateless, развёрнуты в двух ЦОД за балансировщиком. MS SQL — с репликацией/Always On. Kafka — кластер с репликацией. АБС остаётся вертикально масштабируемой; её нагрузка регулируется адаптером.
    
9. **Безопасность.** TLS на всех внешних и внутренних HTTP-границах, секреты в vault, PII шифруется, аудит действий, rate limiting на публичных формах.
    
10. **Документация и контракты.** OpenAPI для всех API, C4-диаграммы, ADR, runbooks — обязательная часть поставки.


### <a name="_bjrr7veeh80c"></a>**4. Альтернативы**

Альтернативные решения^

| Альтернатива                                          | Почему отклонена                                                                                                                                                               |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Прямой вызов API АБС из интернет-банка                | АБС перегружена, масштабируется только вертикально; прямой онлайн-вызов создаёт риск для работоспособности банка                                                               |
| Реализовать ставки в АБС                              | Увеличивает нагрузку на АБС, привязывает изменения ставок к релизному циклу АБС, усложняет разграничение доступа. Выбран отдельный Сервис ставок с асинхронной синхронизацией. |
| Полный перевод интернет-банка на микросервисы в MVP   | Слишком большой scope и риск для MVP; ломает текущую аутентификацию и сессии. Выбран гибрид: монолит ИБ + новые backend-сервисы.                                               |
| Использовать Kafka внутри интернет-банка              | Текущая платформа ИБ несовместима с Kafka (S-03). ИБ общается с новыми сервисами по REST; Kafka остаётся во внутреннем контуре.                                                |
| Batch-интеграция заявок с АБС раз в сутки             | Не обеспечивает своевременные статусы и СМС; для депозитов нужна near-real-time обработка. Выбран адаптер со staging-таблицами и частым заданием.                              |
| Отдельный депозитный портал с SSO                     | Дублирует аутентификацию и UX, увеличивает стоимость и риски. Выбраны депозитные экраны внутри существующего ИБ                                                                |
| Использовать систему кол-центра как очередь бэк-офиса | Система кол-центра предназначена для звонков, а не для бэк-офиса депозитов. Выбран отдельный UI Сервиса заявок для бэк-офиса.                                                  |

# 5. Недостатки, ограничения, риски

|Риск / ограничение|Влияние|Митигация|
|---|---|---|
|**Интернет-банк остаётся в одном ЦОД в MVP**|Доступность всего ИБ 99,9% не гарантируется; при сбое ЦОД клиенты не смогут подать заявку через ИБ|Новые сервисы активно-активны; сайт продолжает работать; в следующей фазе — дублирование ИБ в резервном ЦОД и глобальная балансировка|
|**АБС-адаптер зависит от задания АБС**|Задержка статусов; при остановке задания заявки «зависают»|Мониторинг очереди staging, алерты, регламент перезапуска; идемпотентная обработка; статус «В обработке» для клиента|
|**Запись в staging всё ещё нагружает Oracle АБС**|При росте объёма заявок нагрузка на АБС растёт|Throttling в адаптере, очередь Kafka, ограничение параллелизма, поэтапное увеличение частоты задания|
|**Kafka — новая технология для банка**|Операционная сложность, нужна экспертиза|Обучение, runbooks, managed-подход, пилот на депозитном MVP; Java-команда уже есть|
|**Событийная согласованность**|Клиент может видеть статус с задержкой; возможны повторные события|Идемпотентные потребители, outbox, статусная модель с промежуточными состояниями, информирование клиента|
|**Устаревание кэша ставок**|Клиент может увидеть старую ставку|TTL, инвалидация по событию, версионирование ставок, проверка актуальности при подтверждении заявки|
|**СМС-доставка и OTP**|Недоставка СМС, попытки подбора кода|Повторная отправка, лимиты попыток, блокировка, альтернативный канал, мониторинг доставляемости|
|**Публичная форма сайта**|Спам, мошеннические заявки, нагрузка|Rate limiting, CAPTCHA, валидация, антифрод-правила, ручная модерация в кол-центре|
|**PII на сайте**|Утечка данных|TLS, минимизация данных, шифрование at rest, маскирование логов, аудит доступа|
|**Дубли заявок**|Двойные заявки и депозиты|Ключ идемпотентности, уникальный ID заявки, дедупликация на стороне сервиса и АБС-адаптера|
|**Зависимость от подрядчика системы кол-центра**|Изменения в интеграции требуют участия подрядчика|Контракт API, версионирование, тестовый стенд, запасной вариант — выгрузка заявок в систему кол-центра через файл/API|
|**MVP сохраняет ручную обработку бэк-офисом**|Нет мгновенного открытия депозита; операционные издержки сохраняются|Это осознанное ограничение MVP; следующая фаза — автоматическое подтверждение ставок и открытие без бэк-офиса|
|**Разграничение доступа депозитного и кредитного бэк-офиса**|Риск нарушения требований безопасности|RBAC в Сервисе ставок, аудит, раздельные роли, согласование с ИБ|
|**Рост количества новых сервисов**|Увеличение поверхности атаки и операционной сложности|API Gateway, единые политики безопасности, централизованная наблюдаемость, минимальное количество сервисов в MVP|
|**Документация и ADR устаревают**|Снижение поддерживаемости|Обязательный ревью ADR при изменениях, OpenAPI в CI, актуализация C4|
|**KYC только офлайн**|Новый клиент не может полностью открыть депозит онлайн|Законодательное ограничение; в MVP — гибридный сценарий «сайт → звонок → отделение»; в будущем — видеоидентификация|
